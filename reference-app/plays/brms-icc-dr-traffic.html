IBM Cloud · PowerVS offshoot

BRMS + ICC backup and cloud restore

On-prem IBM i saves with BRMS and Cloud Storage Solutions for i (5733-ICC), then ICC copies virtual volumes into Cloud Object Storage through a VPC VPN and a COS VPE. A PowerVS IBM i NFS LPAR is only on the restore path: it stages the QCLDBIPL boot images so a new LPAR can network-install, then remaining data comes back from COS.

How to read this

Two conversations with the customer: the nightly save never touches PowerVS. The DR restore lives entirely in IBM Cloud after the bucket is written.

  1. Backup entry: IBM i ICC, not a public COS URL. Traffic is IPsec to the VPC VPN gateway, then east to the COS VPE on tcp/443.
  2. Enforcement: VPN policy/routes (interesting traffic = IBM i subnet ↔ VPE subnet), VPC NACL/security group 443 to the VPE, IAM/HMAC on the bucket.
  3. Why PowerVS is dark on backup: ICC talks to object storage. The NFS LPAR is a restore helper, not a backup proxy.
  4. Why restore cannot skip NFS: IBM i cannot D-mode IPL from COS. QCLDBIPL optical must be copied down (CPYFRMCLD), cataloged, and NFS-exported before the target LPAR network-installs.
  5. Why Transit Gateway is on the drawing: PowerVS does not host VPEs. PER workspace → TGW → VPC → VPE is the private path for CPYFRMCLD. It is not on the on-prem backup path.
  6. Why public COS is denied: Keep the ICC resource URI on the private/direct endpoint so save data does not hairpin the public internet after the VPN.
